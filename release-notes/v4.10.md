# PaperScrape v4.10

Maintenance. Nothing looks different — the scene, the sprites and every setting are exactly as they
were in v4.9 — but the GPU renderer now cleans up after itself properly when Android takes the
wallpaper's drawing surface away and gives it back.

## The wallpaper stopped letting go of the GPU

Android destroys and recreates a live wallpaper's drawing surface whenever it feels the need to —
rotating, unlocking, changing screen resolution, opening the wallpaper picker. Each time that
happened, PaperScrape started a second renderer and simply walked away from the first one, which
carried on holding a graphics context and a full set of loaded textures for as long as the app was
running. Nothing recovered them.

There is now one renderer per wallpaper window for that window's whole life, and a replacement
surface is handed to the renderer that already exists. Coming back is also faster, because the
textures no longer have to be uploaded to the GPU again.

## A graphics hiccup no longer switched the GPU off for good

If anything went wrong while preparing a frame — most often the graphics driver resetting, which
phones do — the wallpaper gave up on the GPU permanently and finished the session on the slower
software renderer. It looked the same, but it cost more battery, and the only way back was
re-selecting the wallpaper.

A renderer that has already drawn at least one frame now rebuilds its graphics context and carries
on, up to three times. A device that genuinely cannot use the GPU still falls back to software
immediately, exactly as before.

## Freeing memory under pressure actually frees memory now

When Android asked the app to release memory, PaperScrape ran the release at a moment when it had no
GPU context to run it against. The textures were never actually freed, but the app forgot it was
holding them — the worst of both. Worse, if rebuilding the small internal texture used for flat
colour failed, the renderer went on believing it was fine and drew those shapes black, with nothing
able to repair it.

The release now happens at the one point in the frame where it is valid, a request made at a bad
moment waits rather than being thrown away, and a failure to rebuild is treated as a failure instead
of being ignored.

## Two smaller fixes in the same area

The software renderer kept drawing into a surface that had already been destroyed, at full frame
rate, until the wallpaper was hidden — wasted work, and wasted battery.

And when a surface was replaced quickly enough that the renderer never saw the gap — which is the
normal case for a rotation or a resolution change — it carried on drawing into the window that had
gone. Depending on the device that cost a dropped frame, a full reload of every texture, or, after a
few of them, the permanent switch to software described above.

## What did and did not change

Everything in this release is about how the renderer manages its GPU resources and its lifecycle —
when a graphics context is created, reused, rebuilt or released, and when a drawing surface is handed
over or let go. That is the only kind of change here.

No scene artwork, sprite, colour or animation logic was changed, and nothing about how a scene is
composed or drawn was altered. Every scene therefore looks and moves exactly as it did in v4.9.

No setting was added, renamed or moved, backups made with earlier versions import unchanged, and
Live Weather behaves exactly as it did in v4.9.

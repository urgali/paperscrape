# v4.3 — settings that stay, cars that read right, and files you can move

`versionCode = 34`, `versionName = "4.3"`. Baseline: v4.2 (`versionCode = 33`).

Three things: a data-loss defect, a proportion defect, and the two file formats
that let a user move their app and share a theme.

---

## 1. A per-theme customization no longer disappears when you touch another theme

**Reported as** "the last update overwrote my saved settings for `beach`".

**Reproduced on an emulator before anything was changed**, and it is not an update
bug:

```
after customising beach:   houses 0.21   hillsDay ff112233
after ONE slider on winter: houses 0.93   hillsDay ffe9f1f7
beach now resolves to:      its factory default, exactly
```

An install-over-install does not touch DataStore, `android:allowBackup` is `false`
so no cloud restore can either, and no startup path writes a per-theme setter. What
an update reliably *does* cause is the user opening the app and browsing their
themes — which is all it took.

**The cause.** The only storage a per-theme edit ever reached was a single flat set
of DataStore keys with one `pending_customization_theme_id` marker naming whichever
theme they belonged to. `ensureFreshPendingTheme` — added in **v2.12** to stop the
opposite bug, one theme's values *leaking* into another — wiped every one of those
keys whenever a setter fired for a different theme. Below "Save this theme as…" in
the gallery, there was no per-theme persistence at all.

**The fix.** The wipe now **archives first**. The outgoing theme's state is written
to its own key as JSON — reusing the serialisation `CustomThemeStore` already uses,
which is versioned and round-trip tested — and restored when that theme is edited
again. `resolveActiveCustomization` gained that archive as a tier between the live
edit and the saved entry. `resetAllCategories` takes the theme it is resetting and
only clears the scratch space when it belongs to that theme.

Purely additive: an install that has never written one of these keys simply has
none, so no destructive migration was needed and none was added.

**Guaranteed now:** every built-in theme and every custom theme keeps its own
customization; switching themes, reopening the app and installing a new version
over the old one all preserve it; and the only thing that removes it is the user
pressing reset.

## 2. Cars no longer look smaller than the people walking behind them

**Measured on rendered frames before changing anything.** Both draw paths reproduce
`SceneSpace`'s projection to within a pixel of antialiasing — an adult pedestrian
measured 22 px against 21.1 predicted, a child 17 against 16.7, a far-lane car 22
against 20.4 plus 2.5 px of police light bar. The implementation was not the problem.

`SceneSpace.PERSON_METRES_TALL` was. It read `1.9f` while its own comment three
lines above said **1.75 m**, and that 8.6% inverted exactly one comparison — the one
the report is about. A car in the **far lane** stands nearer the viewer than a
pedestrian on the **far pavement**, so it must be drawn larger; at 1.9 m the
pedestrian won that comparison (62.7 reference px against the car's 61.1) and a car
with somebody visible behind it read as a toy. At the documented 1.75 m it is 61.1
against 57.7.

| | ground row | before | after |
|---|---|---|---|
| adult pedestrian, far pavement | 637 | 22 px | 20 px |
| child, far pavement | 639 | 17 px | 16 px |
| child, near pavement | 654 | 19 px | 18 px |
| car, far lane | 667 | 22 px | 22 px |
| car, near lane | 689 | 24 px | 24 px |
| driver's face, near lane | — | 4 px | 4 px |
| driver's face, far lane | — | 3 px | 3 px |

**Nothing about the vehicles changed.** `CAR_METRES_TALL` over 48 sprite units is an
honest roof-to-wheel-contact reading of the artwork, the two lanes keep their exact
ratio, and the driver and passenger keep their scales — they read correctly now
because what they are judged against shrank, not because they moved. A bust is 0.43 m
of head and shoulders, which is right for a 1.75 m adult and slightly short for a
1.9 m one.

## 3. Backup, and sharing a theme

Two formats, deliberately not one — different contents, different audiences,
**separate schema versions and separate `kind` markers**, so each can change without
the other and importing one where the other is expected is refused by name.

**App backup** (*Advanced & about → Backup*) carries every global preference, every
theme's own customization, and every saved theme. It carries **no** runtime state:
no resolved GPS fix, no fix timestamp, no live-weather status, nothing from the
updater. It does carry the user's **weather API keys** and custom location, because a
backup that dropped them would not restore a working app — and the export dialog
says so before writing the file.

**Theme file** (*Themes → any theme's menu → Export theme*) carries the resolved
scene, layout and customization, and **nothing personal at all**. An exported theme
keeps working when the built-in it came from is redrawn in a later release, because
the file holds the actual scene rather than a reference to a built-in id;
`sourceThemeId` is recorded for display only. An import always adds a **new,
independent** theme and never replaces one, with duplicate names disambiguated
rather than refused.

Both use the Storage Access Framework, so the app asks for no filesystem permission.
Import is two steps by construction: the file is read and validated, a dialog shows
what it contains, and nothing is written until the user confirms. Every refusal ends
with "Nothing changed", which is true because parsing and applying are separate
steps. Across the two DataStores — which have no shared transaction — the import
snapshots the current state, writes both, and rolls the snapshot back if the second
write fails.

## 4. A saved theme no longer freezes the traffic density into the terrain

Found while validating this release, diagnosed on v4.2, and **still present in v4.3
until now** — so it is fixed here rather than left for a later one.

Saving a theme ("Replace with current", "Save current look as…") wrote
`rawLayout.cars.filter { keepCar(it) }` into the stored layout. A layout is an
*inventory*; a customization is the *view* of it, and for cars collapsing the two is
not harmless: `hasRoad` is `layout.cars.isNotEmpty()` and the road's lane pair comes
from the same list. A theme saved while the Cars density was low — or with Cars
switched off — was stored with **no cars at all**, so it lost its road and every
vehicle **permanently**. Putting the density back to 100% afterwards filters a list
that no longer has anything in it, while the settings screen goes on reading
"On - 100%" because the customization was never what broke.

Measured on the real `beach` layout: saved at 50% → 6 cars kept, at 20% → 1, at
**10% → 0**, with Cars off → **0**.

`SceneSpace.roadEdgeMarginFraction` already states the rule this restores: *"the lane
pair must come from the theme's whole car list, never from the cars a density setting
happens to have kept… the road is terrain, and terrain does not depend on how much
traffic is on it."* `drawRoad` obeyed it at frame time; the save path did not.

**The fix:** the car list is saved whole. The saved theme looks exactly the same,
because the entry carries its own customization and `keepCar` applies it at render
time to the same full list — asserted as an equality of the visible car set, not as
an approximation.

**And the installs already damaged are repaired.** A built-in override with an empty
car list, whose built-in still defines cars, has them restored **on load** — the
single funnel every reader goes through, so it happens even if the app starts as a
wallpaper and the user never opens the gallery. Only `layout.cars` is touched: the
customization, the name, the colours and the static objects are left exactly as they
are, so a theme repaired at 10% density gets its road back and keeps showing 10% of
the traffic. A standalone custom theme has no canonical layout to compare against and
is **never** speculatively repaired.

No schema bump and no migration entry: the repair is idempotent, so running it on
every load is both simpler and safer than writing to disk on a startup path.

Changed: `WallpaperPrefs`, `CustomThemeStore`, `CustomThemeRegistry`, one constant in
`SceneSpace`, three UI screens, four new files, tests, goldens, docs, version.

location, the updater, `compileSdk`, `targetSdk`, CI, dependency versions.
